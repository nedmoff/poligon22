# Карта уязвимостей

Этот документ описывает, какие уязвимости referee будет искать в вашем
сервисе. Мы не закладываем их в код — они возникают естественным образом,
если реализовывать фичи «в лоб». Ваша задача — не допустить их.

Referee атакует каждую команду каждые 60 секунд. Каждая успешная атака
referee — штраф для команды. Каждая отбитая атака — бонус.

---

## 1. IDOR — Insecure Direct Object Reference

**Где:** `GET /api/v1/chats/<id>/messages`

**Наивная реализация:**

```python
@app.get("/api/v1/chats/<int:id>/messages")
def messages(id):
    return Message.query.filter_by(chat_id=id).all()
```

**Что делает referee:**

1. Регистрирует двух пользователей `referee_a` и `referee_b`.
2. Создаёт между ними приватный чат и пишет секретное сообщение.
3. Заходит третьим пользователем `referee_c`.
4. Пробует `GET /api/v1/chats/<id>/messages` под сессией `referee_c`.

**Уязвимо, если:** вернулся 200 и сообщения видны.
**Защищено, если:** 403 или 404.

---

## 2. Broken Authorization — отправка в чужой чат

**Где:** `POST /api/v1/messages` с полем `chat_id`.

**Наивная реализация:** проверить только существование чата, но не участие
текущего пользователя в нём.

**Что делает referee:**

- Под сессией `referee_c` шлёт сообщение в чат между A и B.

**Уязвимо, если:** 201 — сообщение принято.
**Защищено, если:** 403.

---

## 3. SQL-инъекция в поиске

**Где:** `GET /api/v1/messages/search?q=...`

**Наивная реализация:**

```python
sql = f"SELECT * FROM message WHERE text LIKE '%{q}%'"
db.session.execute(sql)
```

**Что делает referee:** шлёт пейлоады:

- `' OR '1'='1`
- `1' UNION SELECT 1,username,password_hash,4,5 FROM user--`
- `' AND 1=0 UNION SELECT NULL,username,NULL,NULL,NULL FROM user--`
- `'; SELECT sleep(5); --`

**Уязвимо, если:**

- сервер вернул 500,
- в ответе видны данные других пользователей,
- в ответе отражается SQL-ошибка или трейсбек.

**Защищено, если:** 200/400 и в ответе только свои сообщения.

---

## 4. Stored XSS в сообщениях

**Где:** отображение сообщений в HTML-странице чата.

**Наивная реализация:** `{{ message.text | safe }}` или
`render_template_string(message.text)`.

**Что делает referee:**

1. Отправляет сообщение `<script>alert(1)</script>`.
2. Запрашивает HTML-страницу чата.
3. Ищет в HTML подстроку `<script>alert(1)</script>` без экранирования.

**Уязвимо, если:** тег отражён как есть.
**Защищено, если:** `&lt;script&gt;` (Jinja экранирует по умолчанию).

---

## 5. Path Traversal в экспорте

**Где:** `GET /api/v1/chats/<id>/export?format=...`

**Наивная реализация:**

```python
filename = request.args.get("format")
return send_file(filename)
```

**Что делает referee:** подставляет в `format`:

- `../../../../etc/passwd`
- `..\..\..\..\windows\win.ini`
- `/etc/passwd`
- `/etc/hostname`

**Уязвимо, если:** вернулся файл вне `instance/` — проверяем по сигнатурам
`root:x:`, `[fonts]`, `localhost`.

**Защищено, если:** 400 или строго фиксированный формат (`txt`, `json`).

---

## 6. Отсутствие rate limiting на логине

**Где:** `POST /login`

**Наивная реализация:** без ограничений.

**Что делает referee:**

- Делает 50 попыток логина `referee_bf` с неверным паролем за ~10 секунд.
- Замеряет среднее время ответа.

**Уязвимо, если:** все 50 запросов прошли без задержки и без ответа 429.

**Защищено, если:**

- хотя бы один ответ 429, или
- есть заголовок `Retry-After`, или
- среднее время ответа > 300 мс (значит, есть искусственная задержка),
- или после N попыток пользователь блокируется.

## 7. Session cookie без флагов

**Где:** любой ответ, устанавливающий сессионную cookie.

**Наивная реализация:** Flask по умолчанию ставит `HttpOnly`, но не ставит
`SameSite` и `Secure`.

**Что делает referee:**

- Логинится и разбирает заголовок `Set-Cookie`.

**Уязвимо, если:** отсутствует `SameSite=Lax` или `SameSite=Strict`.
**Защищено, если:** `SameSite=Lax` или строже.

**Подсказка:**

```python
app.config['SESSION_COOKIE_HTTPONLY'] = True
app.config['SESSION_COOKIE_SAMESITE'] = 'Lax'
```

---

## Как защищаться

- Проверять авторизацию **на каждом** эндпоинте, а не только при входе.
- Использовать ORM (SQLAlchemy) вместо raw SQL, либо параметризованные
  запросы — никогда не склеивать SQL через f-string.
- Не использовать `|safe` в Jinja для пользовательских данных.
- Валидировать имена файлов через белый список разрешённых значений.
- Ограничивать частоту логинов (например, свой счётчик попыток в БД
  или `flask-limiter`).
- Явно настраивать флаги сессионной cookie.

---

## Чего referee НЕ делает

- Не удаляет данные.
- Не выходит за пределы эндпоинтов из ТЗ.
- Не атакует ваш сервер вне HTTP.
- Не мешает вам работать во время фазы разработки.
